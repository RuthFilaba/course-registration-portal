## Task 1 — Build an accessible interface

### 1.1 Structure (already satisfied by index.html)
- Landmarks: `<header class="site-header">`, `<nav aria-label="Primary">`, `<main id="main">`, `<footer class="site-footer">`.
- Heading order: a single `<h1>Course Registration</h1>` inside `main`; no heading level is skipped.
- Every input has an explicit `<label for="id">` bound to a matching `id` (`name`, `student-id`, `programme`, `course`) — this is what "linked labels" means: a screen reader announces the label when the control receives focus, and clicking the label focuses the control.
- `required` is set on all four fields. `novalidate` is set on the `<form>` deliberately, because Task 2 requires the *server* to be the real validation boundary — the browser's built‑in bubble validation is disabled so the custom `#status` messaging is what students see, but this means students must confirm empty submissions are still rejected by `server.js`, not silently accepted.
- The submit control is a genuine `<button type="submit">`, not a `div` with a click handler, so it is reachable by keyboard and announced with the "button" role automatically.
- Feedback lives in `<p id="status" role="status" aria-live="polite">`, which is updated via `setStatus()` in `app.js` using `textContent` — never HTML — so user‑entered values can never be interpreted as markup (this is also the injection‑safety justification examiners will look for).

### 1.2 Responsive and keyboard testing

### 1.3 Fetch helper, loading/error states, storage
`app.js` imports with `import { fetchCourses, submitRegistration } from "./api.js";` inside a `<script type="module" src="app.js">` tag — this is required because `import`/`export` syntax is only valid in module scripts, and modules are deferred and origin‑restricted (no `file://` execution, which is why the lab insists on serving over `http://localhost:5500` rather than opening `index.html` directly).

- **Loading state:** `setStatus("Submitting registration…", "loading")` plus `button.disabled = true` before the request, re‑enabled after.
- **Error state:** branches for `result.status === 409` (duplicate), `result.data?.error` (validation message from the server), and a generic network‑failure message — all three are distinguishable to the user rather than one blanket "something went wrong."
- **Safe DOM update:** `setStatus()` uses `el.textContent = message`, never `innerHTML`, so a student ID or name containing `<script>` cannot execute.

**localStorage vs sessionStorage.** `localStorage.setItem("programme", data.programme)` persists the value with no expiry, across tabs and across browser restarts, until explicitly cleared — this is why reloading the page after a successful submission still shows the previously chosen programme (`restoreProgrammePreference()` reads it back on load). `sessionStorage` uses the identical API (`getItem`/`setItem`/`removeItem`) but scopes the value to one tab's lifetime: it is cleared the moment that tab or window closes, and a value written in one tab is not visible in a second tab even on the same page — `localStorage` is shared across every tab of the same origin. Neither is sent to the server automatically (unlike cookies), and both only ever store strings.

To demonstrate persistence: submit the form (or just change the programme dropdown), reload the page, and show the dropdown pre‑selected to the saved value; then open DevTools → Application → Local Storage → `http://localhost:5500` and show the `programme` key.
`[SCREENSHOT PLACEHOLDER: Application tab, Local Storage, key "programme" with its saved value, next to the reloaded page showing that programme pre-selected]`

### Browser → web server → application → data store
```
[Browser]                 [Web server / API]              [Application logic]        [Data store]
 index.html/app.js  --fetch-->  server.js (Express)  -->  route handlers        -->  in-memory

 client-side is a         returns JSON + status code      (duplicate check,             static array)
 CONVENIENCE only                                          required fields)
      ^                                                          |
      |__________________ JSON response, status code ____________|
```

**Where validation belongs:** client‑side checks (`required` attributes, disabling the button, a friendly inline message) exist only to give the user fast feedback and reduce unnecessary requests — they are never trustworthy, because a user can submit directly with `curl`, disable JavaScript, or edit the DOM. The **server** is the only place validation can be enforced, which is exactly why `server.js` re‑implements every rule in `validateRegistration()` independently of anything the form does, and why Task 2.2 requires students to bypass the form with `curl`/Postman and prove the server still rejects bad data.

### Standards bodies
| Standard | Body | Notes |
|---|---|---|
| HTML | **WHATWG** (HTML Living Standard); historically also W3C, which now publishes a snapshot of the WHATWG standard | Defines elements, semantics, forms, accessibility tree mapping |
| ECMAScript (JavaScript) | **Ecma International**, Technical Committee 39 (**TC39**) | Defines the language: modules, `fetch` is *not* ECMAScript itself (see below) |
| HTTP | **IETF** (Internet Engineering Task Force) — HTTP/1.1 is RFC 9110/9112, HTTP/2 is RFC 9113, HTTP/3 is RFC 9114 | Defines methods, status codes, headers, caching semantics |
| Fetch API / DOM / Storage (localStorage, CORS) | **WHATWG** | The Fetch and Storage standards are browser‑platform standards, separate from both HTML and ECMAScript |

### 2.1 Testing with cURL first
```bash
# 1. success
curl -i http://localhost:3000/api/courses

# 2. valid POST (201 + Location)
curl -i -X POST http://localhost:3000/api/registrations \
  -H "Content-Type: application/json" \
  -d '{"name":"Jane Phiri","id":"STU002","programme":"Cybersecurity","course":"ICS441"}'

# 3. invalid POST (400)
curl -i -X POST http://localhost:3000/api/registrations \
  -H "Content-Type: application/json" \
  -d '{"name":"","id":"STU003"}'

# 4. duplicate POST (409) — repeat request #2 unchanged
curl -i -X POST http://localhost:3000/api/registrations \
  -H "Content-Type: application/json" \
  -d '{"name":"Jane Phiri","id":"STU002","programme":"Cybersecurity","course":"ICS441"}'

# 5. missing record (404)
curl -i http://localhost:3000/api/registrations/STU999

# 6. DELETE (204, then repeat for 404)
curl -i -X DELETE http://localhost:3000/api/registrations/STU002
curl -i -X DELETE http://localhost:3000/api/registrations/STU002
```

**`response.ok` and 204:** `response.ok` is `true` only for status 200–299, so it correctly treats `204` as success without the client needing to special‑case the number. `api.js` already guards `if (response.status === 204) return { ok: response.ok, status: 204 };` **before** calling `response.json()`, because a 204 response has no body and `.json()` on an empty body throws a `SyntaxError` — this is exactly the bug the brief is testing for.

**Idempotency.** Repeating identical `POST` requests is *not* idempotent even though the HTTP status might differ each time (201 the first time, 409 after) — what makes an operation idempotent is whether **repeating it produces the same server state as doing it once**, not whether it returns the same status code. `PUT` is idempotent because replacing a record with the same payload twice leaves the server in the same state both times, even though the response is `200` both times. `DELETE` is idempotent in the same sense — deleting an already‑deleted record leaves the *state* "record absent" unchanged, even though the second call returns `404` instead of `204`. `POST` is defined as **not** idempotent because each call is intended to create a new resource: calling it twice is intended to (and, in a system without a duplicate check, would) create two resources — the 409 here is this prototype's business rule for detecting an unwanted duplicate, not evidence of idempotency.

### 2.3 `/inspect` diagnostic route
`server.js` already exposes `app.all("/inspect", ...)`, echoing method, path, query, headers and body. Test it with both content types:

```bash
curl -i http://localhost:3000/inspect -H "Accept: application/json" \
  -H "Content-Type: application/json" -d '{"a":1}'

curl -i http://localhost:3000/inspect -H "Accept: text/html" \
  -H "Content-Type: application/x-www-form-urlencoded" -d "a=1&b=2"
```
`Content-Type` describes what the **client is sending** in the request body (parsed by `express.json()` vs `express.urlencoded()` respectively — this is why both parsers are mounted in `server.js`); `Accept` describes what representation the **client would prefer back** in the response. **URL anatomy**, using `http://localhost:3000/api/registrations/STU001?verbose=true#summary` as the example:
- **scheme:** `http`
- **host:** `localhost`
- **port:** `3000`
- **path:** `/api/registrations/STU001`
- **query:** `?verbose=true`
- **fragment:** `#summary` — never transmitted to the server; open Network and confirm the recorded request URL stops at the query string, because the fragment is resolved entirely client‑side (it exists to let the browser scroll to/target a location within the already‑fetched document).

## Task 3 — Caching and browser boundaries

### 3.1 ETag / Cache-Control / no-store
`GET /api/courses` already computes a SHA‑1 `ETag` over the course array and sets `Cache-Control: public, max-age=60`.

1. First request — note the returned `ETag` value, e.g. `"a1b2c3..."`.
2. Repeat the request with `curl -i http://localhost:3000/api/courses -H 'If-None-Match: "a1b2c3..."'` and show `304 Not Modified` with **no response body**.
   `[SCREENSHOT PLACEHOLDER: terminal/DevTools showing 304 response, empty body, same ETag]`
3. Edit an entry in the `courses` array in `server.js`, restart the server, repeat step 1 and show the ETag has changed and the response is `200` with the new data.
   `[SCREENSHOT PLACEHOLDER: 200 response with updated course data and a different ETag value]`

**Freshness vs revalidation:** `max-age=60` defines a *freshness window* — for 60 seconds after the first response, a caching client is permitted to reuse its stored copy without contacting the server at all. Once that window expires, the cache doesn't necessarily discard the data; it *revalidates* by sending `If-None-Match` with the stored ETag, and the server either confirms nothing changed (`304`, saving the response body's bandwidth) or supplies a new representation (`200`). Freshness avoids a round trip entirely; revalidation still makes a round trip but avoids re‑sending the payload when unnecessary.

`Cache-Control: no-store` on the registration routes (added in §0) tells every cache — browser, proxy, CDN — never to store the response at all, which is correct for per‑student data that should never be served stale or to the wrong client from a shared cache.

### 3.2 CORS
With the interface on `:5500` and the API on `:3000`, this is a cross‑origin request, so the browser enforces CORS on top of whatever the server allows.

1. **Before configuring CORS:** temporarily comment out the `app.use(cors({...}))` block (or set `origin` to something else) in `server.js`, restart, and submit the registration form from `http://localhost:5500`. Capture the console error (`... has been blocked by CORS policy ...`) and the preflight `OPTIONS` request in Network showing it fails or is rejected.
   `[SCREENSHOT PLACEHOLDER: DevTools console CORS error, plus Network tab showing the failed/blocked OPTIONS preflight]`
2. **Restore the CORS config** exactly as supplied — `origin: "http://localhost:5500"`, explicit `methods`, `allowedHeaders: ["Content-Type", "If-None-Match"]`, `credentials: true` — restart, and repeat the same submission successfully. Capture the now‑successful `OPTIONS` preflight (204, with `Access-Control-Allow-Origin`, `Access-Control-Allow-Methods`, `Access-Control-Allow-Headers` in the response) followed by the actual `POST`.
   `[SCREENSHOT PLACEHOLDER: successful OPTIONS preflight response headers, followed by the actual POST succeeding]`
3. **Compare with cURL:** run the same POST directly with `curl` against `:3000`. This is the key concept to write up: cURL has no origin and no same‑origin policy to enforce, so it never sees a CORS error even when a browser would.

Do **not** disable browser security flags (e.g. `--disable-web-security`) to "fix" this — the brief explicitly forbids it, and doing so would misrepresent how CORS actually works.

### 4.2 Written explanations

- **`Secure` in production:** without `Secure`, a cookie is sent over plain HTTP as well as HTTPS, so it could be read by anyone intercepting unencrypted traffic on the network path (a coffee‑shop Wi‑Fi attacker, a compromised router). `Secure` restricts the browser to attaching the cookie only on HTTPS requests, closing that plaintext‑interception window. This lab uses `http://localhost` deliberately, where `Secure` would prevent the cookie from being sent at all — which is why it is correctly omitted here and should be explicitly documented as an intentional lab‑only choice.
- **`HttpOnly`:** marks the cookie invisible to `document.cookie` and any other JavaScript API, so a cross‑site‑scripting (XSS) bug elsewhere on the page cannot read and exfiltrate the session cookie — the cookie is still sent automatically by the browser on requests, just never exposed to script.
- **`SameSite` is not full CSRF protection:** `SameSite=Lax` stops the cookie being attached on most cross‑site *subrequests* (images, cross‑site `fetch`/`XHR`, form POSTs from another site) but still allows it on top‑level navigations such as a user clicking a link — and older browsers, misconfigured proxies, or subdomains under attacker control can still create request paths where the cookie is attached unintentionally. `SameSite` reduces the attack surface; it does not replace explicit CSRF defences such as a server‑issued, per‑form CSRF token that is verified independently of any cookie.
- **Cookie sessions vs bearer tokens:** a session cookie is opaque to the client, attached automatically by the browser on every matching request (convenient, but that automatic attachment is exactly what makes CSRF possible), and is naturally revocable server‑side by deleting the session record. A bearer token (e.g. a JWT in an `Authorization: Bearer ...` header) must be attached manually by client code on every request, is not vulnerable to CSRF in the same way (an attacker's page cannot make the browser attach a header it doesn't control), but if stored in `localStorage` it becomes readable by any script on the page — i.e. more exposed to XSS than an `HttpOnly` cookie — and revoking a self‑contained token before its expiry generally requires a server‑side blocklist, since the token itself carries its own validity.

**HTTP/2 multiplexing:** HTTP/1.1 needs a separate TCP connection (or strictly serialised requests per connection, in practice mitigated by opening several parallel connections) to avoid head‑of‑line blocking at the application layer. HTTP/2 opens one TCP connection and interleaves many concurrent request/response streams over it, each broken into frames tagged with a stream ID — so multiple resources can be in flight on the same connection at once without waiting for each other, cutting connection‑setup overhead and improving utilisation of that one connection.

**HTTP/3 over QUIC/UDP:** HTTP/3 keeps HTTP/2's stream multiplexing but replaces the TCP transport with **QUIC**, which runs over **UDP**. This matters because in HTTP/2‑over‑TCP, a single lost packet blocks *all* streams on that connection until it's retransmitted (TCP head‑of‑line blocking at the transport layer, even though HTTP/2 solved it at the application layer) — QUIC's per‑stream loss recovery means a lost packet only stalls the one stream it belongs to. QUIC also folds the TCP handshake and TLS handshake into fewer round trips. Report only the protocols DevTools actually shows (`h2`, `h3`, `http/1.1`); never write down `h3` if the site or your network path didn't actually negotiate it.
